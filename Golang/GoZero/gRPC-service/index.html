客户端实现

gRPC客户端封装在zrpc.Client 中，自动集成了服务发现、负载均衡、熔断器和链路追踪

直连模式

直连模式会显式指定服务地址，不走注册中心，客户端会和endpoints列表中的地址建立gRPC连接

缺点为地址写死，迁移后需要手动更新代码或重新部署

适用于本地开发与单元测试和服务器地址固定不变的场景

服务发现模式

客户端通过服务注册中心动态获取可用服务节点，具体ip集中在app.yaml中

运行流程：

  • 客户端启动时连接etcd
  • 根据key从etcd拉取一组节点（服务端启动时注册的）
  • 内置的负载均衡器会从这组地址中选择以恶搞发起调用
  • etcd中的节点发生变更时，客户端自动更新本地地址列表

优点在于适合动态扩缩容，配合Breaker中间件，可以自动摘除故障节点，与整个go-zero生态结合紧密

适用于生产环境

newClient的方法

  • NewClient会返回client和err，需要手动处理错误，启动时连接失败不会panic
  • MustNewClient在内部调用client，如果出错则直接panic

大部分项目使用第二个即可，需要特殊处理初始化错误时，才使用第一个

发起调用

在gozero中HTTP服务调用下游RPC服务的写法：

在逻辑层结构体，包含两个重要成员：

  • svcCtx *ServiceContext包含所有依赖
  • ctx context.Context由框架传入，携带了本次HTTP请求的全部上下文
    • 当 go-zero 的 HTTP 网关收到请求时，会从请求头中提取 traceparent、tracestate 等 W3C TraceContext 字段，生成带有 SpanContext 的 context，存入 l.ctx
    • 当调用 gRPC 客户端时，go-zero 的 gRPC 拦截器会自动将 l.ctx 中的 trace 信息注入到 gRPC 的 metadata 中，生成 traceparent header
    • 下游 RPC 服务收到请求后，若同样使用了 go-zero 并开启了 trace 中间件，会自动解析该 header，并创建子 Span，将其父 Span 设为当前 HTTP Span

注意：

  • l.ctx除了trace，还会携带deadline（由http超时或上层调用设置），gRPC会调用并自动遵循，超时返回context.DeadlineExceeded

  • 若需要在RPC传递业务自定义元数据，可以使用metadata.NewOutgoingContext(l.ctx) 将 kv 放入 context，gRPC 拦截器会自动传递。

  • KeepaliveTime：gRPC长连接每隔多久发送一次ping，防止负载均衡或防火墙因空闲断开连接

错误处理

gRPC的错误是一个结构化状态，包含一个标准的status.Code和描述

  • status.FromError(err) 从 gRPC 错误中提取出 *status.Status 对象
  • st.Code() 得到对应的 gRPC 状态码
  • 可以根据这些状态码使用NewCodeError将错误转换成自己需要的格式，然后再返回给 HTTP 客户端。
  • 内置的errorx会和httpx配合，将带code的错误直接映射为HTTP响应状态码

熔断器

gozero的RPC客户端默认启用了熔断器，基于自适应熔断，逻辑是：

在滑动时间窗口内（默认为10秒），如果下游请求的错误率超过50%，熔断器就会打开，拒绝后续请求。一段时间后会进入半开状态，试探性放行少量请求，如果成功率回升则关闭

拦截器

有些场景需要向每个gRPC请求的metadata中注入业务信息，如x-request-id，认证token等，gozero可以使用WithUnaryClientInterceptor添加自定义拦截器

  • metadata.AppendToOutgoingContext 向 gRPC 的 outgoing metadata 中添加 key‑value 对
  • invoker(ctx, method, req, reply, cc, opts...) 继续后续的拦截器链并最终发起调用

常用场景包括：

  • x-request-id ：全链路追踪 ID，便于日志关联
  • Authorization / Token：服务间认证
  • x-user-id：传递当前操作用户身份

直连

直连下有两种模式

地址解析模式：

其中Target是gRPC内置的URI风格解析器标识，语法为schema://authority/endpoint

如dns:///127.0.0.1:8080：告诉gRPC的resolver通过DNS查询解析这个地址，当指定的是IP地址时，DNS解析直接返回该IP，类似直连；当指定的是域名时，才会做真正的DNS解析

  • 若DNS返回多个IP，gRPC会在它们之间做客户端负载均衡
  • 适合K8s Headless Service场景配合DNS服务发现使用
  • 其中target和endpoints互斥，同时设置时，前者会被忽略

多节点直连模式：

gozero会遍历给出的endpoints列表，将每个地址构造为gRPC的sunConn，客户端内置的负载均衡策略（P2C，即随机选择两个，选择其中最优的一个）会在这些节点间发送请求，若某个节点故障，gRPC层面的连接重试和gozero的熔断器会将其临时剔除

这样处理配置直观，且不需要DNS解析或注册中心，多个节点之间自动负载均衡，配合上熔断器可以提高可用性，但是地址列表是静态的，需要手动更新配置并重启

etcd 服务发现

go-zero下，可以使用etcd做服务发现，初始化如下面的例子：从 etcd 中找到名为 greet.rpc 的服务节点，然后建立 gRPC 连接并调用其 Ping 方法

  • 首先通过conf和fillDefault将RPC客户端配置结构体填入默认值，防止服务异常
  • clientConf.Etcd用于配置etcd：
    • Hosts：etcd的集群地址
    • Key：服务在etcd中的注册key（服务名）
    • 其余字段当etcd开启ACL/TLS时才需要填写
  • 接下来使用MustNewClient创建一个gRPC客户端，此时内部执行的动作：

    • 把该ClientConn包装进zrpc.Client并返回

  • greet.NewGreetClient 是根据protobuf文件编译出的 gRPC client 构造函数，负责将结构体方法映射成 RPC 调用
  • client.Ping发送请求并等待响应，超时使用gRPC配置中的timeout，gozero自动在拦截层添加context超时

原生支持

可以不适用go-zero的zrpc的client初始化，而直接使用grpc.ClientConn原生支持

原生grpc去掉了服务发现，负载均衡，拦截器等能力，适合连接固定地址的场景

  • grpc.Dial用于建立连接：
    • 第一个参数是目标服务地址，直连而不走服务中心
    • grpc.WithBlock()使Dial阻塞等待连接成功，如果不加这个选项，Dial会立即返回，底层在后台异步建立
    • grpc.WithTransportCredentials(insecure.NewCredentials())：指定传输证书，这里使用insecure.NewCredentials()无认证，生产环境下可以使用credentials.NewTLS(...)
    • 返回的 conn 是 *grpc.ClientConn，它负责实际的网络连接管理与复用
    • 注意：使用WithBlock() 且没有设置超时时，如果目标服务不存在或网络不通，Dial 可能一直阻塞而不会返回，建议配合带超时的ctx：ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
  • client := greet.NewGreetClient(conn)创建业务客户端，该方法是通过protobuf文件生成的client桩代码，接受一个grpc.ClientConn接口，返回一个可以调用具体方法的客户端对象，只负责将方法调用封装成 gRPC 请求并发送
  • client.Ping发送一个ping请求等待响应，这里也是没有超时的，最好自己传入一个带超时的ctx

使用场景：

  • 本地功能调试
  • 服务发现由自己实现

服务端

go-zero 在标准 gRPC 服务端之上封装了弹性治理、服务注册和链路追踪等能力

大体流程：定义 Protobuf → 用 goctl 生成服务骨架 → 填充业务逻辑 → 配置 etcd 注册 → 启动 RPC 服务

生成代码

通过goctl生成代码：

目录结构：

  • greeter/：存放 *.pb.go 和 *_grpc.pb.go，这是由 protoc 生成的纯 gRPC 代码，不渗透任何 go-zero 关联
  • internal/config：定义从 yaml 读取的配置结构体。例如 Name、ListenOn、Etcd
  • internal/svc：保存 ServiceContext 结构体，相当于一个“依赖容器”，把一个服务需要用到的数据库、缓存等资源组装好。
  • internal/logic：业务代码唯一需要写的地方。包含每个 RPC 方法的逻辑
  • internal/server：由 goctl 生成，负责将 gRPC 请求转交给 logic 层处理，本质是适配器。
  • greeter.go：启动入口，会组装整个服务并启动监听

配置文件

配置文件处于etc/*.yaml

服务启动流程

启动入口greeter.go入口的流程如下：

  • 首先加载配置，构建serverContext

  • 注册GreeterServer的实现：greeter.RegisterGreeterServer(server, server.NewGreeterServer(svcCtx))

  • 然后自动向etcd注册greeter.rpc服务，并定期续约，监听注册的地址提供请求

配置

zRPC 服务配置主要用于控制 rpc 的监听地址、服务注册发现、链路追踪、日志、中间件等

RpcServerConf

这里是服务总配置的入口

  • service.ServiceConf是通用配置，决定了服务全局行为
  • ListenOn是监听地址，若只写端口号表示监听所有网卡
  • etcd是服务注册与发现配置，不需要向etcd注册时可以为空，此时客户端通过直连地址访问服务
  • auth表示开启rpc调用认证，客户端必须要在gRPC的metadata中携带token，服务端才会接受请求
  • Redis保存了合法token的映射，服务端会去Redis校验
  • StrictControl指定校验失败时的策略，true表示失败即拒绝，false记录waring但不拒绝，适合调试场景
  • Timeout指服务端处理单个请求的超时时间
  • CpuThreshold是自适应降载阈值，默认900，表示当CPU利用率达到90%时开始拒绝部分服务
  • Health表示是否注册gRPC健康检查服务，默认开启，这样k8s或gRPC health client可以探测服务存活状态：grpc_health_v1.NewHealthClient(conn).Check(...)
  • Middlewares控制服务器内置中间件开关，生产环境保持默认即可

EtcdConf

这里是etcd的详细配置

  • Hosts：etcd 集群节点地址
  • Key：服务唯一标识，建议与服务 Name 保持一致（如 greeter.rpc），客户端也使用这个 Key 去 etcd 中寻找服务
  • ID：可选的实例 ID，如果不填，go-zero 会使用本机 IP + 端口自动生成唯一 ID，用于多实例注册时区分
  • 其余字段：当 etcd 开启 TLS/ACL 时需要提供
  • 注意：gozero的etcd注册路径一般是/services/{Key}/{ID} 的形式，key相同但id不同会被视为同一服务的不同副本

RedisKeyConf

用于认证存储，RedisKeyConf是当你需要使用 redis 来管理 rpc 认证时需要配置的参数

  • Key 是存储 token 的 redis key 前缀，例如 rpcAuth:
  • 服务端会根据客户端传来的 token，去 redis 的 ${Key}${token} 中查找是否存在且未过期

ServerMiddlewaresConf

中间件配置，控制常用中间件的开启和关闭

stub实现

通过goctl生成的代码就不用stub方法了，goctl会全部实现

代码存在于/internal/server/greetserver.go下，用于实现 gRPC 框架定义的服务接口greet.GreetServer，并把请求转交给 internal/logic 层的业务代码。

结构体定义：

  • svcCtx保存了服务上下文，包括配置、数据库连接、redis等共享依赖，它是 go-zero 依赖注入的核心：所有 logic 方法都通过它访问全局资源
  • greet.UnimplementedGreetServer是官方gRPC生成器在pb文件中定义的，即使未来proto新增了rpc方法但你的代码没有实现，也不会panic而是返回未实现，这是一种向前兼容

构造函数：

将 ServiceContext 注入到服务端对象中，之后每个 RPC 方法都可以使用这个上下文

核心方法：

假设是一个Ping方法，gozero的处理流程如下：

  • server 层：只做“路由转发”，代码千篇一律，交给 goctl 生成
  • logic 层：包含全部业务规则，由开发者编写
  • 当 .proto 接口变更，goctl 会自动更新 server 层并生成新的 logic 占位代码，你只需在新占位方法中实现业务

对于逻辑层：

  • NewPingLogic 接收 context 和 svcCtx
  • Ping() 方法直接从 GreetServer.Ping() 调过来，in 就是解码后的请求参数，返回即为响应体

对于客户端：

目录中的greetclient/greet.go是为调用方生成的客户端代码，为了方便业务方生成的代码，当你不是服务端实现者时，只需要greetclient.NewGreetClient(...) 就能请求这个 RPC 服务

中间件的使用

gozero中有大量拦截器，对应grpc两种调用模式：

拦截器类型 作用
UnaryXXXInterceptor 拦截普通一元 RPC 请求（一个请求一个响应）
StreamXXXInterceptor 拦截流式 RPC 请求（客户端/服务端双向流）

RpcServerConf.Middlewares中可以通过配置控制五个内置中间件：

  • Trace：链路追踪
  • Recover：捕获 panic
  • Stat：服务调用统计
  • Prometheus：指标暴露
  • Breaker：熔断

其中这五种可以通过配置开启关闭，默认开启

实际项目中，一般将自定义拦截器定义在独立文件/internal/middleware/exampleinterceptor.go，在main入口中引入，保证文件整洁

注册自定义中间件：

顺序如下：

  1. MustNewServer 创建服务对象
  2. 在回调中注册业务服务和调试反射
  3. 在服务启动前，通过 AddUnaryInterceptors 和 AddStreamInterceptors 注册自定义中间件
  4. Start() 后生效

定义自定义Unary中间件：

  • ctx：gRPC请求的上下文，可以读取metadata
  • req：已解码的请求消息对象
  • info：包含当前请求对应的服务方法信息info.FullMethod
  • handler：业务处理函数，调用handler后会继续向后执行直到进入logic

定义自定义Stream中间件：

  • srv：当前服务实例，通常用 server 中的 handler 对象
  • ss：服务端流对象，用于收发消息。
  • info：方法信息
  • handler：流式 RPC 的实际处理函数，需要你手动调用，期间可在外层包裹流程

流式拦截器

流式 handler 不像一元 handler 那样直接调 handler(ctx, req)，而是 handler(srv, ss)。业务代码通过 ss.Recv() 和 ss.Send() 来处理流中的多个消息

  • srv：服务端实现对象
  • ss：grpc.ServerStream接口，对应流式调用的服务端流对象
  • info：当前调用信息，包含流式RPC的方法流，是否是客户端流等信息
  • handler：最终执行流处理的函数

客户端

有时候需要给所有发出去的RPC请求附加一些公共信息：比如Token认证、请求ID、业务租户ID或客户端来源/版本，客户端拦截器可以让统一在RPC调用前拦截并修改context/metadata，然后继续发送请求

一元拦截器

例如：在每次对外RPC请求中注入Token或传递请求头

  • ctx：当前调用上下文
  • method：将要调用的gRPC方法名
  • req：请求信息
  • reply：响应信息
  • cc：gRPC连接对象
  • invoker：下一环节的调用函数，调用才能发送请求
  • opts：调用选项

流程：

可以理解为：invoker 就是后续真正的 gRPC 调用链路，你只是“劫持”了它的 ctx 参数，替换成带 metadata 的ctx

流式拦截器

  • ctx：调用上下文
  • desc：流描述，描述是客户端，服务端还是双向流
  • cc：连接对象
  • method：方法名
  • streamer：真正的流创建函数，返回一个grpc.ClientStream
  • opts：调用选项

一元拦截器是一次请求一次性处理，invoker完成整个调用，而流式流通过streamer创建流，后续还会通过 stream.Send、stream.Recv 等进行多次消息交互，因此：

  • 在拦截器中，你会修改ctx，然后传给streamer，返回ClientStream
  • 后续所有sendmsg，recvmsg都是用这个流，metadata已经在这个流理的context中固定了

因此流式拦截器适合在流建立前统一处理
